1. PROBLEM STATEMENT & OBJECTIVES
--------------------------------------------------------------------------------
- Objective: Resolve business entity records from 3 noisy, independent sources
  (Source 1 reference anchors against Source 2 and Source 3).
- Scope:
  * Training Sources: US and India records (2,206,821 Source 1 entities).
  * Test Sources: US, India, and France (1,732,544 Source 1 entities against ~9.97M S2/S3 records).
  * Country generalization: Pipeline must handle open-set country strings (including unseen France).
- Metric: Macro-averaged F_0.5 Score:
    F_0.5 = (1.25 * Precision * Recall) / (0.25 * Precision + Recall)
  * Precision-heavy metric: Penalizes false merges 2x more than missed matches.
  * Singletons: S1 entities with zero true matches score 1.0 if predicted empty, and 0.0 if any false match is predicted.

- Key Noise Characteristics Discovered:
  1. Name corruptions: Legal suffix variations (Corp, LLC, Pvt Ltd, SA, SARL),

  3. Multilingual diacritics: French accents (é, è, ç, à, etc.) handled via Unicode NFKD.

3. SYSTEM ARCHITECTURE & PIPELINE MODULES
--------------------------------------------------------------------------------
Our end-to-end solution is modularized in `code/business_entity_resolution/src/`:

- `preprocessor.py`:
  * Unicode NFKD diacritic removal (vital for French generalization).
  * Legal suffix standardization (corp -> corporation, ltd -> limited, pvt -> private).
  * Address expansion & standardizing US state abbreviations and street types.

- `blocking.py`:
  * Country-partitioned candidate generation (matches never cross countries).
  * Discriminative Token Inverted Index: indexes rare/discriminative tokens
    (ordered by lowest posting count / highest IDF) to retrieve top 35 candidates
    per entity in sub-milliseconds without memory explosion.

- `feature_engineering.py`:
  * 30 dense pairwise features computed via C++ accelerated RapidFuzz & Jellyfish:
    - Name metrics: Levenshtein ratio, Jaro-Winkler, Token Sort Ratio, Token Set Ratio,
      Partial Ratio, Token Jaccard, Token Containment, Length difference & ratio,
      Exact match, First word match, Soundex phonetic match.
    - Address metrics: Levenshtein, Jaro-Winkler, Token Sort/Set, Jaccard, Containment,
      Exact match, Length diff.
    - Digit / Structural metrics: Number intersection, Number Jaccard, Number mismatch flag.
    - Interaction features: Composite harmonic similarity (`overall_avg_sim`),
      Name x Address Jaro-Winkler product, Name x Address Token Set product.

- `metrics.py`:
  * Exact competition F_0.5 macro-averaging metric suite including singletons and
    blocking candidate recall evaluators.

- `train_and_validate.py`:
  * Rigorous holdout validation experiment with threshold grid search and feature importance analysis.

- `pipeline.py`:
  * Full production pipeline: loads data via PyArrow, trains regularized LightGBM on
    ~1,000,000 reference pairs, and runs streaming inference across test countries,
    directly writing `output/matching_results.tsv` and `output/candidate_pairs.tsv`.

5. TECHNICAL CHALLENGES OVERCOME
--------------------------------------------------------------------------------
- Challenge 1: Memory Overflow on Large Sparse Matrix Multiplication
  * Issue: Multiplying 10k x 3.8M sparse matrices in SciPy attempted to allocate 79.3 GiB RAM.
  * Solution: Developed a Discriminative Token Posting List blocker that queries only the
    rarest, high-IDF tokens per entity. Memory dropped to <500 MB and speed surged to 100k queries/sec.
- Challenge 2: Massive TSV Read Latencies (~1.3 GB per source)
  * Solution: Integrated PyArrow C++ engine in Pandas (`engine='pyarrow'`), reducing file
    loading times from ~45 seconds down to 3–8 seconds per file.
- Challenge 3: Overfitting Prevention & Cross-Country Generalization
  * Solution: Applied LightGBM tree constraints (max depth 8, num leaves 63, feature fraction 0.80,
    bagging fraction 0.80, L1=0.1, L2=1.0) on scale-invariant string distance ratios.
